# Just Spec

[English](./README.md)

**Persistent What. Ephemeral How.**

Just Spec は、人間のレビューを、レビューする価値のある唯一の成果物である spec に集中させる、Claude Code 向けの仕様駆動開発プラグインです。

```text
Request
   ↓
/just-spec:spec
   ↓
Behavioral Contract   ← 人間がレビューするのはここだけ
   ↓
/just-spec:build
   ↓
Implementation + AC Evidence
```

多くのワークフローは、人間の注意力を要件、設計、タスク、生成されたコードへと分散させます。コードレビューのコストは生成量に比例して増えますが、spec のレビューはいつでも1画面ぶんで一定です。Just Spec は、注意力を「量に比例する場所」から「量に依存しない場所」へ移します。

ここから3つのことが導かれます。

- **レビュー対象は spec 一点。** 承認すべき計画もタスク一覧もないので、契約と注意力を奪い合うものがありません。
- **完了とは、計画を実行したことではなく、契約を満たしたこと。** 受け入れ基準が検出器であり、build はそれに対して実行され、基準ごとに根拠を報告します。
- **人間は意思決定者であり、ドキュメントのレビュアーではない。** Just Spec は判断点を選択肢と推奨つきで運んできて、人間は選ぶだけです。人間がドキュメントを読んで問題を探しに行く工程は作りません。

## 何を残すのか

Just Spec が残すのは、実装が正しいかどうかを判断するために必要な契約だけです。

```text
Goal
Requirements
Acceptance Criteria
Material Decisions
Constraints
Out of Scope
```

設計書も、実装計画も、タスク分解も、テスト計画も作りません。これはそれ自体が目的なのではなく、レビューをどこに置くかから導かれる結果です。成果物が1つ増えるたびに、注意力を向けるべき場所が1つ増えます。

どう実装するかは、実装の時点でモデルがコードベースを見て判断します。

## 2つのコマンド

Just Spec には2つのスキルしかありません。

### `/just-spec:spec`

要求と既存のコードベースから、振る舞いの契約（Behavioral Contract）を作成します。

```text
/just-spec:spec <変更したい内容>
```

コードベースや既存の挙動、確立された慣習から妥当に判断できることは質問しません。

人間に確認するのは**本質的な曖昧さ**、つまり実装の正しさを変えうる決定と、あとから覆すのに大きなコストがかかる決定です。

- ユーザーから見える振る舞い
- 公開されている、あるいは他と共有している取り決め
- 権限とアクセス制御
- データの保持期間
- 後方互換性
- 取り消せない破壊的な操作
- 業務上の方針
- 覆すコストが高い実装上の選択（トランザクション境界、イベント発行方式、並行制御、キャッシュ整合性、スキーマ設計など）

最後の一群が重要なのは、いま外から見て違いが観測できないからです。コストは、その選択を覆すことになったときに、あとから来ます。

質問は一度に1つずつ、推奨つきの選択形式で提示されます。妥当な案が複数あるときは、各案の利点・欠点と推奨理由も添えられるので、回答は文章を書くことではなく選ぶことになります。

回答を得るたびに、あらかじめ用意した質問票をなぞるのではなく、残っている曖昧さを評価し直します。質問数に固定の上限はありません。

仕様の分割も、質問の数や技術的なレイヤーではなく、目的がまとまっていて単独で検証できる成果かどうかで判断します。

作成された仕様は次の場所に保存されます。

```text
.just-spec/specs/<slug>.md
```

### spec の読み方

spec には2種類の内容が混ざります。人間が質問に答えて確定した決定と、Just Spec がコードベースから推論して書いた記述です。自分の決定を確認するのは一瞬ですが、推論の検分こそ人間が要る部分です。そのため、推論には印が付きます。

```text
- **R4:** 🤖 支払いが保留中のあいだ、削除は拒否される。
```

`🤖` は「この項は Just Spec の推論であり、人間による確認を推奨する」という意味です。印のない項は、あなたの回答から確定したものです。

### `/just-spec:build`

準備の整った契約をもとに実装します。

```text
/just-spec:build <仕様のパスまたはslug>
```

モデルは必要に応じて内部で計画を立てますが、その計画は一時的なもので、成果物としては保存されません。

```text
Behavioral Contract
      │
      ├──────────────▶ Implementation
      │
      └──────────────▶ Verification
                              │
                              ▼
                         AC Evidence
```

実装の最後に、受け入れ基準の1つひとつについて、それを満たしていると言える根拠を報告します。

## 設計思想

### 「何が正しいか」は残し、「どう作るか」は残さない

永続化するのは、**何が成り立っていなければならないか**です。

**どうやってそれを成り立たせるか**は、その時点のコードベースを見てモデルが判断します。

ファイル単位の実装計画や作業手順はすぐに古びます。振る舞いの契約は、実装が変わっても価値を保ちやすいものです。

実装手順は一時的なままにします。ただし、覆すコストが高い判断の理由はそうではありません。それは捨てた案とともに Material Decisions として残ります。コードは何を選んだかを示しますが、何を捨てたのか、なぜ捨てたのかは示さないからです。

### 実装の詳細ではなく、正しさを左右する曖昧さを解く

正しさに実質的な影響を与えること、そして覆すコストが高いことは、人間が決めるべきです。

クラス名やファイル配置、ヘルパーの切り方、内部の抽象化といったやり直しのきく選択は、モデルに任せます。

### 計画の遵守ではなく、振る舞いの充足で完了を判断する

完了の基準は次ではありません。

> 計画のすべての手順を実行したか。

完了の基準はこちらです。

> 実装は受け入れ基準を満たしているか。

Just Spec は契約に照らして振る舞いを検証し、基準ごとに根拠を報告します。

### テストは実装ではなく契約から導く

Just Spec はテストファーストや TDD、レッドグリーンリファクタを必須とはしません。

重要なのはテストを**いつ**書くかではなく、その期待結果が**どこから来ているか**です。

```text
              ┌── Implementation
Spec / AC ────┤
              └── Tests
```

実装と検証は、どちらも同じ契約から導出されるべきです。

テストは内部の実装をなぞるのではなく、安定した境界を通して観測できる振る舞いを検証します。

## このワークフローが検出できないもの

テストは契約に対する検出器です。実装が受け入れ基準に誠実かどうかは示せますが、受け入れ基準そのものが欠けていることは示せません。

契約の欠落は、失敗するテストも、エラーも、レビュー指摘も生みません。成功と見分けがつきません。それを捉えられる場所は、spec を読んでいるあいだの人間のレビューだけです。

これがこのワークフローの賭けであり、Just Spec が人間に求めるレビューが spec ただ1つである理由です。ほかのすべては、そのための注意力を残しておくために組まれています。

## Just Spec と Plan Mode

Plan Mode は権限モードです。編集を許可する前に Claude Code が調査して提案し、人間がその提案を承認します。

Just Spec は権限モードではなく、両者の違いは能力の差ではありません。何を永続化し、何を質問し、何を完了条件とするかという、成果物プロトコルの違いです。

| | Plan Mode | Just Spec |
|---|---|---|
| 永続化されるもの | 承認した計画（保持しているあいだ） | リポジトリにコミットされる振る舞いの契約 |
| 人間が求められること | 編集開始前に実装方針を承認する | 正しさを左右する曖昧さを、推奨つきの選択肢から決める |
| 「完了」の意味 | 通常どおり、人間が判断する | すべての受け入れ基準を満たしたという根拠 |

この2つは併用できます。Plan Mode は Claude Code がいつ編集してよいかを定め、Just Spec はその変更が何を満たすべきかを定めます。

長時間の自律的な作業、大規模な移行、複雑な並列実行、あるいは調整そのものが難所になる変更では、詳細な計画は今も有効です。

## インストール

Claude Code でマーケットプレイスを追加します。

```text
/plugin marketplace add Basio0916/just-spec
```

Just Spec をインストールします。

```text
/plugin install just-spec@just-spec
```

必要に応じてプラグインを再読み込みします。

```text
/reload-plugins
```

## 使い方

まず仕様を作ります。

```text
/just-spec:spec 14日間の復元期間つきでアカウント削除を追加したい
```

正しさを左右する曖昧さがあれば、振る舞いを一意に定めるために必要な質問だけを確認します。

仕様が整ったら実装します。

```text
/just-spec:build account-deletion
```

実装が終わると、変更の要約と、受け入れ基準ごとの根拠が報告されます。

## 向いていない場面

Just Spec は、あらゆる開発に最適なワークフローを目指しているわけではありません。適用するかどうかを判断するのは人間であって、ツールが要求を拒むことはありません。次のような作業では、より厳密な計画とレビューのほうが適しています。

- 長時間の無人実行
- 大規模な移行作業
- 複数エージェントによる並列開発
- セキュリティ上重要な変更
- 複雑なアーキテクチャの変更
- 高い監査性や承認プロセスが求められる開発

Just Spec は、こうしたワークフローが不要だと主張するものではありません。もっと狭い問いを検証しています。

> **人間のレビューを1つの契約に集中させたとき、日常的な開発ではそれで足りるのか。**

## 現状

Just Spec はまだ実験的なプロジェクトです。

いまは意図的に、次の2つのコマンドだけを公開しています。

```text
/just-spec:spec
/just-spec:build
```

目指しているのは、ワークフローを増やすことではありません。人間の注意力を、それを使うことで結果が変わる唯一のドキュメントに置き続けることです。
