# Goal

Just Spec を「ループエンジニアリングの上流工程」に絞る。build コマンドを廃止し、実行は利用者が Claude Code 公式の `/goal` を直接使う形にする。`/just-spec:spec` は spec を確定させた時点で、そのままコピーして実行できる `/goal` の起動行を提示する。実行が無人になるため、実行時の規律を spec ファイル自身に集約し、質問判定と UI 系 AC の水準を無人実行に耐える水準へ引き上げる。

## Context

Just Spec は `/just-spec:spec` と `/just-spec:build` の2コマンドからなる Claude Code プラグインで、実体は `plugins/just-spec/skills/` 配下のスキル文書・テンプレート・リファレンスと、README（英日）・`docs/` のドキュメント群である。`scripts/validate.mjs` が必須不変フレーズ・語数予算・スキル構成を CI で検査しており、現在はスキルが `build` と `spec` の2つであることを要求している。

`/goal` は Claude Code 2.1.139 以降のローカルスラッシュコマンドで、条件文の上限は 4,000 文字。設定すると条件文が Stop フックのプロンプトとして登録され、ターンが終わるたびに条件文が注入され、評価器が成立を判定するまで作業が続く。したがって条件文は「判定基準」であると同時に「作業指示」でもある。評価器は独立にコマンドを実行したりファイルを読んだりせず、会話に出力された内容のみから判定する。

spec ファイルを参照させた `/goal` 実行が、条件文への翻訳なしで全 AC 充足まで完走することは実験で確認済みである。

build を廃止すると、実行に届く成果物は spec ファイルと短い条件文だけになる。現在 build スキルと `references/verification.md` が担っている実行時の規律（Evidence 表、AC の判定区分、期待結果の出所、停止の作法、spec の status 更新）は、行き先を決めない限り失われる。

観測済みの不具合が2つある。ひとつは、もっともらしいデフォルトを持つ業務判断（延滞一覧の並び順、予約の受付時刻の出所）が質問判定をすり抜けて AI 推定になったこと。もうひとつは、画面表示系 AC の検証層が実装ごとに割れ（マークアップ／サービス層）、サービス層で検証した側では押すと必ずエラーになるボタンの表示が検出されなかったことである。

## Requirements

### build の廃止と /goal 起動行の提示

- **R1:** build コマンド（`plugins/just-spec/skills/build/` 配下の一式）を削除し、プラグインが公開するコマンドを `/just-spec:spec` の1つにする。
- **R2:** `/just-spec:spec` は、spec が `ready` に達した時点で、コピーしてそのまま実行できる `/goal` の起動行を提示する。`ready` 以外の状態では提示しない。🤖
- **R3:** 起動行の条件文は定型であり、差し込むのは対象 spec のファイルパス（必要なら overview のパス）のみとする。spec の内容を翻訳・転記・列挙せず、AC の数や spec の規模が変わっても長さが変わらない。
- **R4:** 条件文は次を要求する。対象 spec ファイルを読むこと / その全 AC が PASS であること / AC 別の Evidence（結果と根拠）が報告されること / spec の Constraints に違反していないこと / 充足不能・解決不能な失敗の場合は完了とせず経緯と質問を報告して停止すること / 部分充足での完了宣言を行わないこと。
- **R5:** 🤖 条件文は対象 spec の実装を命じる指示文として書く。`/goal` は条件文を Stop フックのプロンプトとして注入するため、条件文がそのまま作業の駆動に使われる。
- **R6:** 条件文は `/goal` の 4,000 文字上限に余裕をもって収まる長さに保つ。
- **R7:** `/just-spec:spec` は実行機能を持たない。実行の駆動・反復・完了判定はすべて `/goal` と利用者の側にある。

### 実行時規律の spec への集約

- **R8:** spec テンプレートに固定の完了節を設け、完了の定義を次のとおり要求する。全 AC が実行済みの根拠つきで PASS であること、AC 別の Evidence 表（AC / 結果 / 根拠）が報告されること、部分充足は完了ではないこと。
- **R9:** 固定節に停止規律を含める。ある AC を満たすと別の AC または Constraint に必ず違反する充足不能を検出した場合、完了を宣言せず、矛盾の内容と試行の経緯を報告して停止する。
- **R10:** 固定節に反復失敗時の停止を含める。同一 AC への修正が繰り返し失敗する場合、無際限に試行を続けず、試行の経緯・検出器の出力・原因の仮説を添えて停止する。停止の報告は失敗の宣言ではなく、人間が判断すべき点（仕様を変えるか、制約を緩めるか）を明示した質問として構成する。
- **R11:** 固定節に検証の出所を含める。期待結果は spec から導き、現在の実装や観測された出力から取らない。根拠には実行した検査の名前・コマンド・観測結果を示し、実行していない検査を PASS として報告しない。
- **R12:** 固定節に、完了時に spec の `status` を更新することを含める。全 AC が PASS なら `verified`、そうでなければ `partial` とする。
- **R13:** build スキルとともに `plugins/just-spec/skills/build/references/verification.md` を削除する。固定節に集約しない詳細（Evidence 境界の階層、テストダブルの扱い、既存テストとの衝突処理、オラクル独立性の限界）は `docs/VERIFICATION.md` に文書として残す。

### デフォルト持ち判断の質問化

- **R14:** spec スキルの質問判定の説明に次を明記する。一般的・慣習的なデフォルトが存在することは、質問を省略する理由にならない。デフォルトの存在と、条件3（外部から観測可能な影響、または可逆性の低さ）・条件4（誤った仮定のコスト）の成立は、独立に判定する。
- **R15:** すり抜けやすい判断の類型を例示する。一覧の並び順 / 時刻・日付の出所（業務上の現在日と実時刻の使い分け）/ 採番・順序付けの方法 / 同時・同値の場合の優先順位 / 丸め・境界の扱い。
- **R16:** 判定の拡大は、デフォルトを理由とした省略の禁止に限る。条件1（焦点を絞った調査で答えが導ける）で除外される事項、およびクラス名・ファイル配置・ヘルパーの切り方・テスト配置は引き続き質問しない。

### UI 系 AC の観測境界

- **R17:** spec スキルは、画面表示・画面操作に関する AC を生成する際、観測境界（何を実行し、どの出力で確認するか）を AC の文面に含める。
- **R18:** テスト基盤の有無で観測境界の実現可能性が変わる場合、spec フェーズの時点でそれを検出し、検証手段を人間への質問または spec への明示的な記載として確定する。実行フェーズに判断を先送りしない。
- **R19:** 観測境界の明記は UI 系 AC に限る。ドメイン層・サービス層の AC には適用しない。

## Completion

この節は固定です。無人で実行されても契約が完結しているよう、各 spec に残します。

- 完了とは、全 AC が実行済みの根拠つきで `PASS` であり、AC 別の Evidence 表（AC / 結果 / 根拠）が報告されていることです。部分充足（「主要な AC は満たした」等）は完了ではありません。
- 期待結果は spec から導きます。現在の実装や観測された出力を根拠にしません。根拠には実行した検査の名前・コマンド・観測結果を示し、実行していない検査を `PASS` として報告しません。
- ある AC を満たすと別の AC または Constraint に必ず違反する場合、完了を宣言せず、矛盾の内容とそれまでの試行を報告して停止します。
- 同一 AC への修正が繰り返し失敗する場合、無際限に試行せず、試行の経緯・検出器の出力・原因の仮説を添えて停止します。報告は失敗の宣言ではなく、仕様を変えるか制約を緩めるかという人間が判断すべき点を明示した質問として構成します。
- 完了時に、この spec の `status` を全 AC PASS なら `verified`、そうでなければ `partial` に更新します。

## Constraints

- `plugins/just-spec/skills/spec/SKILL.md` は 1250 語以内、`references/ambiguity.md` は 900 語以内を維持する。
- `/goal` の条件文は 4,000 文字上限に余裕をもって収まる長さに保つ。
- 標語 "Persistent What. Ephemeral How." は維持する。
- `README.md` と `README.ja.md` は同等の内容を保つ。
- テンプレートの固定節と観測境界の明記が、spec の1画面性と可読性を損なわない。
- 質問対象の拡大は、デフォルトを理由とした省略の禁止に限る。可逆な実装選択まで広げない。
- 観測境界の明記は UI 系 AC に限り、ドメイン層・サービス層の AC を冗長化しない。
- 既存の `.just-spec/specs/spec-review-focus.md` は書き換えない。

## Out of Scope

- 実行ループの自前実装（停止条件・反復規則・最大試行回数の機構化）。
- `/goal` の内部動作への依存・ハック。評価器の挙動は公式仕様の範囲でのみ前提とする。
- build の代替となる実行コマンドの新設。
- ハンドオフの検証手順1〜4 の実施。実装後に人間が別セッションで行う。
- 同一 spec の複数実装・diff 比較の工程化、およびそのドキュメントでの言及。
- クロスモデル検証・独立レビュー。
- "Just Spec" の改名、および `/just-spec:spec` のコマンド名変更。
- タスク分解・実行計画の導入。
- `docs/EXPERIMENT.md` の書き換え。

## Dependencies and Shared Contracts
