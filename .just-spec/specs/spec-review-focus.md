# Goal

Just Spec を「工程を削った軽量SDD」ではなく「人間のレビューを spec 一点に集中させるツール」として成立させる。具体的には、覆すコストが高い実装選択が人間に届き、その選択を人間が選ぶだけで済み、選択の理由と AI 推論由来の記述が spec 上で識別できるようにし、ドキュメントの位置づけ記述を実態に一致させる。

## Context

Just Spec は `/just-spec:spec` と `/just-spec:build` の2コマンドで構成される Claude Code プラグインで、実装は `plugins/just-spec/skills/` 配下のスキル文書、`templates/spec.md`、`references/ambiguity.md`、および README・`docs/` のドキュメント群である。`scripts/validate.mjs` が文言・語数・構成の不変条件を CI で検査している。

現行の曖昧さ判定は4条件のうち条件3が「外部から観測可能な影響がある」ことを要求しているため、外部挙動が同一で可逆性だけが低い選択（トランザクション境界など）は人間に届かない。また現行の `SKILL.md` Step 3 はすでに「推奨＋2〜4個の簡潔な選択肢」を要求しているが、各案の利点・欠点の比較と推奨理由の根拠づけは求めておらず、質問は本文テキストで提示され回答も自由記述で受けている。

## Requirements

### 曖昧さ判定

- **R1:** 曖昧さ判定の条件3を「外部から観測可能な影響がある、または選択の可逆性が低い（覆すのに大きなコストがかかる）」に拡張する。
- **R2:** 可逆性が低い選択の例示（トランザクション境界、イベント発行方式、ロック/並行制御、キャッシュ整合性、スキーマ設計）をスキル内に含める。
- **R3:** クラス名、ファイル配置、ヘルパーの切り方、テスト配置などの可逆で日常的な選択は、引き続き質問対象にしない。

### 質問の提示と回答形式

- **R4:** 人間への質問は Claude Code の AskUserQuestion ツールで提示し、1回の提示に含める質問は1つとする。ツールが利用できない環境では本文テキストによる提示にフォールバックする。
- **R5:** 推奨案は選択肢の先頭に置き、推奨であることがラベルから分かるようにする。
- **R6:** 条件3を満たし、かつ妥当な選択肢が複数ある場合、各案の利点・欠点と推奨理由を本文に提示し、AskUserQuestion の選択肢は案名と一行要約に留める。
- **R7:** 本文に書く比較は各案数行以内とし、人間が読んで選ぶまでの認知負荷を、比較を伴わない質問と同等以下に保つ。
- **R8:** 推奨理由は spec 内の情報（Out of Scope、既存 Decisions、コードベースの現行標準）に根拠づける。
- **R9:** 単純な Yes/No 質問や事実確認では本文に比較を書かず、選択肢のみで提示する。すべての質問を比較形式にしない。
- **R10:** 人間は選択肢を選ぶだけで回答でき、自由記述を強制されない。自由記述が必要な回答は AskUserQuestion の「Other」または任意回答として受ける。
- **R11:** この提示規則は `/just-spec:spec` と `/just-spec:build` の両方の質問に適用する。

### 判断の記録

- **R12:** Material Decisions の各エントリは、選んだ案 / 捨てた主要案 / 選択の根拠 / 成立の前提となる不変条件 / 見直すべき条件 を記録できる形式を持つ。該当しない項目は省略できる。
- **R13:** 選択の根拠は、AI が提示した各案の利点・欠点・推奨理由から AI が記録に落とす。人間に「なぜその案を選んだのか」を質問しない。記録上、根拠が AI 提示由来であることが分かる。
- **R14:** 人間が AI の推奨と異なる案を選んだ場合に限り、理由を任意（スキップ可）で添えられる。スキップされた場合は「推奨と異なる選択（理由未記載）」として記録が成立する。
- **R15:** 選択肢提示で人間が選んだ結果は、この形式で自動的に記録される。

### AI 推論由来の記述の識別

- **R16:** AI がコードベースや既存仕様から推論して記述した項に視覚的な印を付ける。人間の回答に基づいて確定した項には印を付けない。
- **R17:** 印の意味（この項は AI の推論であり、人間による確認を推奨する）を `templates/spec.md` のフォーマット説明と README（英日）に記載する。

### ドキュメントの位置づけ

- **R18:** README（英日）の冒頭説明を、レビューを spec 一点に集中させること / 完了の定義は計画の実行ではなく契約の充足であること / 人間は意思決定者でありドキュメントレビュアーではないこと、という位置づけに更新する。
- **R19:** Plan Mode との比較を、Plan Mode は「編集前に調査・提案し承認を得る権限モード」であり、Just Spec との違いは能力ではなく「何を永続化し、何を質問し、何を完了条件とするか」という成果物プロトコルの違いである、という整理に改める。
- **R20:** 検出器（テスト）が検出できるのは契約への適合であり、契約の欠落は検出できないこと、ゆえに spec 確定時の人間レビューがこのワークフローの要であることを README（英日）に明記する。
- **R21:** 標語 "Persistent What. Ephemeral How." を維持したまま、覆すコストが高い判断の理由は Material Decisions として残すことを本文で補足する。
- **R22:** `docs/PHILOSOPHY.md` と `docs/INTERVIEW.md` を、再定義後の位置づけと質問挙動に一致させる。

### specの引き渡し

- **R23:** `/just-spec:spec` の完了報告に、spec がこのワークフローで人間がレビューする唯一の対象であること、および印の付いた AI 推論由来の項を優先して確認してほしいことを示す一文を含める。
- **R24:** この一文は承認ゲートにしない。人間の承認を待たず、`/just-spec:build` の案内は従来どおり同じ報告内で行う。

## Acceptance Criteria

- **AC1:** 外部から観測できる振る舞いは同一だがトランザクション境界の選択が分かれるタスクを `/just-spec:spec` に与えたとき、その選択について人間への質問が発生する。
- **AC2:** ファイル配置やクラス名のみが分かれるタスクを `/just-spec:spec` に与えたとき、その選択についての質問は発生しない。
- **AC3:** 可逆性が低い、または外部挙動に影響する分岐で妥当な案が2つ以上あるとき、本文に各案の利点・欠点と推奨理由が各案数行以内で示され、選択は AskUserQuestion の選択肢（案名と一行要約、推奨案が先頭でラベルから推奨と分かる）として提示される。
- **AC4:** 「削除時に確認を挟むか」のような単純な仕様確認では、本文に利点・欠点の比較が書かれず、AskUserQuestion の選択肢のみで提示される。
- **AC5:** 1回の質問提示に含まれる質問は1つである。
- **AC6:** 人間は選択肢を選ぶだけで回答を完了できる。自由記述を求められるのは、推奨と異なる案を選んだ場合の任意の一言に限られる。
- **AC7:** 同じ提示規則が `/just-spec:build` の実装中に発生する契約上の質問にも適用される。
- **AC8:** 選択肢提示で人間が推奨案を選んだとき、選んだ案・捨てた主要案・AI 提示由来と分かる根拠を含む Material Decisions エントリが記録され、根拠を尋ねる追加質問は発生しない。
- **AC9:** 人間が推奨と異なる案を選んだとき、理由の一言入力が任意として提示され、人間がスキップしても「推奨と異なる選択（理由未記載）」としてエントリが成立する。
- **AC10:** コードベースからの推論を含む spec を生成したとき、推論由来の項と人間の回答で確定した項が印の有無で見分けられる。
- **AC11:** 人間が質問に回答した後、その回答を反映した項には印が付かない。
- **AC12:** 1つの spec は `.just-spec/specs/<slug>.md` の1ファイルに収まり、`design.md` などの新規の永続成果物は生成されない。
- **AC13:** `README.md` と `README.ja.md` の冒頭説明に、「軽量」「削減」を主軸とした自己紹介が残っていない。結果としての軽さへの言及は許容する。
- **AC14:** `README.md` と `README.ja.md` の Plan Mode 比較が、権限モードと成果物プロトコルの違いという整理になっており、Plan Mode の完了判定を断定する記述が残っていない。
- **AC15:** `README.md` と `README.ja.md` に、テストが検出できるのは契約への適合であり契約の欠落は検出できないこと、および spec 確定時の人間レビューが要であることの記述がある。
- **AC16:** `README.md` と `README.ja.md` に標語 "Persistent What. Ephemeral How." が残っており、覆すコストが高い判断の理由を Material Decisions に残す旨の補足がある。
- **AC17:** `docs/PHILOSOPHY.md` と `docs/INTERVIEW.md` に、旧位置づけ（軽量SDDとしての自己紹介）および旧質問挙動（外部観測可能性のみを条件3とする判定、比較と選択肢ツールを伴わない提示）の記述が残っていない。
- **AC18:** `node scripts/validate.mjs` が終了コード0で成功する。
- **AC19:** 公開されるコマンドは `/just-spec:spec` と `/just-spec:build` の2つのままである。
- **AC20:** spec の生成が完了したとき、報告に spec の確認を促す一文が含まれ、その一文が印の付いた項を優先して確認するよう示している。
- **AC21:** その報告は人間の承認を待つ形になっておらず、同じ報告内で `/just-spec:build` の次コマンドが案内される。

## Decisions

- **D1:** ハンドオフの変更5（契約照合の任意ルート）は実装しない — 別エージェントによる検証の価値が薄いという判断。3つ目のコマンドの追加も `scripts/validate.mjs` のスキル構成検査の変更も不要になる。
- **D2:** 文書の更新範囲は README（英日）と `docs/PHILOSOPHY.md`・`docs/INTERVIEW.md` に限定する — 位置づけと質問挙動が実際に変わる文書のみ。`docs/VERIFICATION.md` はテスト由来性の原則が再定義後もそのまま成立し、`docs/EXPERIMENT.md` は実施済みの実験設計の記録であるため据え置く。
- **D3:** 残る5変更を単一 spec とする — 質問判定・回答形式・記録・表示とその文書化が1つのまとまりを成し、独立にリリースできる分割線がない。
- **D4:** 変更2の言う「従来形式」は自由回答ではなく、現行 `SKILL.md` Step 3 が既に要求している「推奨＋2〜4個の簡潔な選択肢」を指す — 現行スキルが選択肢提示を必須にしているため。今回の追加分は各案の利点・欠点の明示と推奨理由の根拠づけである。
- **D5:** バージョンを 0.6.0 に上げ、`package.json` / `.claude-plugin/marketplace.json` / `plugins/just-spec/.claude-plugin/plugin.json` を揃えて `CHANGELOG.md` に追記する — 全リリースでバージョンを上げるリポジトリの慣習と、`validate.mjs` の3マニフェスト一致検査に従う。
- **D6:** 推論印の記法（絵文字・接頭辞・注記のいずれか）と付与粒度は実装時に決める — ハンドオフが明示的に実装時判断としており、可逆である。
- **D7:** 質問は AskUserQuestion で提示し、各案の利点・欠点と推奨理由は本文に置き、選択肢は案名と一行要約に留める。
  - 捨てた主要案: 利点・欠点を AskUserQuestion の各選択肢の `description` に集約し、本文には背景のみ書く案（AI の推奨案）。
  - 根拠（AI 提示由来）: 本文に置くほうが比較と推奨理由を十分な長さで書け、Out of Scope や既存 Decisions への根拠づけ（R8）を自然に置ける。`description` に集約する案は読む場所が1つに収まる反面、説明が長いと表示が窮屈になり推奨理由の置き場が限られる。
  - 備考: 推奨と異なる選択（理由未記載）。
- **D8:** 提示規則を `/just-spec:build` の質問にも適用する — build も実装中の契約上の発見で人間に質問するため、spec 側だけに適用すると同一ワークフロー内で提示面が食い違う。
- **D9:** spec 確認を促す一文は承認ゲートにせず、報告内の案内に留める — ハンドオフの「人間は意思決定者でありドキュメントレビュアーではない」および既存の「チェックポイントは承認ゲートではない」原則に従う。ゲート化すると新しい承認フェーズが1つ増え、2コマンド構成の意味が薄れる。

## Constraints

- `scripts/validate.mjs` の既存検査（必須不変フレーズ、語数予算、スキル構成、旧数値ルールの不在、contract-derived 原則の保持）をすべて満たし続ける。
- `plugins/just-spec/skills/spec/SKILL.md` と `plugins/just-spec/skills/build/SKILL.md` はそれぞれ 1250 語以内、`references/ambiguity.md` は 900 語以内、`references/verification.md` は 1200 語以内を維持する。
- 標語 "Persistent What. Ephemeral How." は変更しない。
- 推論印と Material Decisions の追記が、spec の1画面性と可読性を損なわない。
- `README.md` と `README.ja.md` は同等の内容を保つ。
- 質問対象の拡大は可逆性が低い選択に限り、日常的な実装選択まで広がらない。

## Out of Scope

- 契約照合（contract audit）の任意ルートと、それに伴う3つ目のコマンド。
- Fit 判定（入口での適用可否判定・拒否機構）。
- task フェーズおよびタスク分解の復活。
- `design.md` などの新規の永続成果物。
- 無人・長時間自律実行への対応。
- クロスモデルレビュー（他社エージェント連携）。
- build ループ内への LLM レビューの組み込み。
- 汎用コードレビュー機能（可読性・命名・設計の好み等）。
- Evidence 表の別セッションでの再作成。
- AskUserQuestion の `multiSelect` を使った複数選択、および1回の提示で複数の質問を行うこと。
- `docs/VERIFICATION.md` と `docs/EXPERIMENT.md` の書き換え。
- `plugins/just-spec/skills/spec/examples/account-deletion.md` の書き換え。
- `scripts/validate.mjs` への新規検査の追加（既存検査の維持のみ）。
- 人間に「なぜその案を選んだのか」を尋ねる質問の追加。
